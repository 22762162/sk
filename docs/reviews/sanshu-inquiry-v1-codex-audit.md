# sanshu-inquiry-v1 · Codex 偏袒盲审计

审计日期：2026-08-31
审计对象：`prompts/candidates/sanshu-inquiry-v1.md`（Fable 5 起草，candidate-1，未上线）
审计角色：Codex 主仓交叉评审者；依据 AGENTS.md、INV-10 及公开仓库规范执行。

## 结论

**不通过，存在阻断项；不得进入 Change Eval、接线或本人最终批准。**

主要原因不是发现了对某家供应商的明示偏袒，而是“三段封存”在当前候选中只有提示词层面的要求：同一次模型调用同时收到八字与卦，输出又只有一个未经字段校验的 JSON 对象。禁词检查不能证明未发生未命名的跨段借证，也不能支撑按八字/卦象/综合三表可靠复盘。

本次未修改候选文件；未读取私有评测、Sealed Holdout 或真实数据。

## 通过项

1. **未见供应商/模型明示偏袒。** 候选没有出现 Claude、Gemini、DeepSeek、具体模型名或供应商专属指令；三家使用同一候选、同一根输出结构，符合模型无关的基本方向（候选第 1、50–53 行）。
2. **方法边界有初步意识。** 八字与卦象被分为两个独立字段，综合段才允许合参；六爻与梅花各自列出不同的观察依据（第 14–34、38–40 行）。这是可继续收敛的草案，不足以证明已实现隔离。
3. **安全底线方向基本正确。** 候选要求概率化、不碰生死/确诊/投资买卖/录用淘汰，并要求健康内容附就医提示（第 46–47 行）；现实资料中的指令被当作数据（第 44–45 行）；同时声明不允许自行改装或另起卦（第 40 行）。
4. **有可验证性的意图。** 候选要求应期窗口、限制 `verifiable_events` 为 1–3 条并排除“运势提升”类空话（第 42–43 行）。但事件契约仍不够具体，见下方阻断项。

## 整改项

### R1（高）：方法字段与方法语汇仍有轻微结构偏置

`gua_judgment` 统一使用名为 `yongshen` 的字段；六爻要求“用神取定/取用理由”，梅花则把同一字段解释为“体用”（第 19–23 行）。这不是供应商偏袒，但字段命名以六爻术语为中心，可能给六爻较高的结构显著性，并使梅花输出质量受不对称约束影响。

建议改为中性字段（例如 `method_basis`），或为两种方法分别定义等价的必填字段；`method` 应由受信任的引擎输入回显，不能由模型自行选择。还应在接线协议中固定三家相同的输入、提示词哈希、输出上限与抽样参数，并在 manifest 中留痕；候选目前没有这些约束。

### R2（高）：封存禁词不是可机检的有限契约

“卦名/爻/体用等卦象词”和“干支十神大运等八字词”是开放式类别，不是版本化词表；没有规定大小写/全半角/标点/同义词/嵌套字段的归一化，也没有说明 `dissent_note`、`verifiable_events` 等跨段字段如何计入检查（第 38–39 行）。更重要的是，禁词只能拦截显式词汇，不能证明模型没有利用另一段材料。

建议在接线层做物理隔离：八字调用只接收问题、期限、八字材料；卦调用只接收问题、期限、受信任的卦快照；综合调用只接收两个已封存结果及允许的公共背景。每次调用单独记录 run manifest，并以字段级校验器检查跨段字段。

### R3（中）：安全红线的“继承”实际不会发生

候选头部称继承 `chat.md` 第 3/4/5 条（第 3 行），但运行态加载器只读取 `## system` 之后的正文（`consult-engine/consult.py:95–96`），因此该注释不会进入模型上下文。候选正文还漏掉既有 chat 的“**一定**”以及“不提供改运/消灾类说法”等限制；既有 judge 另明确禁用“预测、改运、消灾、化解、必然、注定”（`prompts/base/arbiter/judge.md:26–30`），候选只列出其中一部分（第 46 行）。

建议将适用红线放入实际发送的 system 正文，统一引用版本化红线策略，并明确新 slot 与既有 chat/judge 的路由边界。不能把“违反字段会被系统整段丢弃”（第 47 行）当作现存能力：当前后端红线过滤只做字符串遮蔽（`backend/app.py:210–219`），没有候选所述的字段级作废器。

## 阻断项

### B1：单次调用无法实现真正的三段封存

候选要求一位模型在同一输出中分别处理八字和卦（第 8–12、38–39 行），但输入同时包含主体八字和完整卦结构（第 8–10 行）。这不是信息隔离；模型即使不在 `bazi_judgment` 中写出卦词，也可能通过卦信息影响判断。当前候选没有调用编排、上下文隔离、封存哈希或“综合只能读取封存结果”的约束。

### B2：没有可执行的输出 schema/validator

候选只展示 JSON 示例；当前 JSON 提取器只验证顶层是 object（`consult-engine/consult.py:107–120`），不会验证必填字段、类型、`additionalProperties`、枚举、数组长度、日期正则、字段间依赖或封存禁词。因此以下要求都无法由现有流程落实：三段必返、confidence 独立、综合置信度上限、事件 1–3 条及“违规整段无效”（第 12–18、26–34、42–48 行）。

必须先定义并钉版候选输出 schema，再实现 fail-closed 校验；至少应覆盖字段必填性、严格字符串/数组类型、`method` 受信回显、日期窗口格式、事件数量与跨段禁词。该契约若改变 `contracts/`，还须按 INV-05 先走 RFC 与契约仓发版。

### B3：材料缺席路径自相矛盾，且综合段可被编造

第 41 行要求缺席时“各字段写 `材料缺席`”，但 `method` 被限定为 `liuyao|meihua`（第 20 行）、三处 `confidence` 被限定为 `low|medium|high`（第 17、24、32 行），`yingqi` 又被要求符合日期窗口或说明原因（第 16、23 行）。同一字符串不能同时满足这些约束。

候选也没有定义“八字缺席/卦缺席/部分结构缺席/输入损坏/方法不匹配”的区别，更没有规定缺一法时 `combined` 必须停止、置为不可评分或由编排层拒绝保存。于是模型可能在材料缺席时仍填充综合结论和事件，直接违反 INV-06 的 fail-closed 要求。

应改为受信输入状态加明确的 `status`/`reason` 结构；缺失或不一致时阻止对应调用，综合调用不得启动，复盘记录为未生成而不是让模型填“材料缺席”到所有枚举字段。

### B4：应期和事件不足以支撑三张分表复盘，并会诱导虚构日期

`bazi_judgment` 与 `gua_judgment` 各有 `yingqi`，但只有 `combined.verifiable_events` 有事件数组（第 14–34 行）。因此八字表和卦象表没有各自的可验证事件、判真伪标准或命中/未命中记录；综合事件也无法归因到某一方法。`event` 的“谁/什么/量级”和“到期能明确判真伪”仍是自然语言要求，没有基线、阈值/单位、时区、窗口边界、观察来源、部分命中规则或去重规则。

另外，第 16、23 行允许“无法给出”，但第 42 行又把无窗口判断视为无效。这个组合会在模型不具备可靠日期依据时施加“必须给日期”的压力，增加编造窗口的风险。

至少应为八字、卦象、综合分别定义事件数组或明确的不可评分状态；事件需绑定稳定 `event_id`、原问题目标、观测窗口（含时区和闭区间规则）、可观察指标/阈值/单位、结果记录与评分规则。无法可靠给出应期时应允许结构化 abstain，并标为不可评分/低置信，而不是以虚构日期换取有效性。

### B5：装卦不可再算没有形成闭环

第 40 行只有“禁止自行改装、另起卦、质疑装卦结果”，没有要求输入带 `method`、规则版本、计算哈希或完整性状态，也没有冲突处理路径。若卦快照部分缺失、字段互相矛盾或与方法不匹配，模型只能被要求接受它，或自行补全；两者都会产生不可审计结果。

这与公开六爻/梅花规范“代码装卦，AI 只解卦”的边界不等价。接线前必须由确定性层验证完整卦快照并绑定哈希；验证失败则 fail closed，不调用解读模型。模型输出不得重新声称计算出的结构字段，或只能引用带 ID 的受信字段；否则无法检测“另算”或结构事实漂移。

### B6：与既有 chat/judge 的接线契约不兼容

候选称“不替代 chat/judge”（第 50–52 行），但既有 `chat.md` 输出 `answer/revised/suggestion`，并要求“先讲为什么，再给结论”（`prompts/base/presenter/chat.md:10–15`）；候选要求 `combined.answer` 第一词就是结论且输出完全不同的嵌套结构（第 12–35 行）。这在独立 slot 中可以共存，但当前没有新 adapter、schema、judge 或 manifest 约定。

既有 `judge.md` 明确是“本场八字会诊”的匿名仲裁者，输入是三方观察，输出 `issues/summary`（`prompts/base/arbiter/judge.md:7–18`），没有三术三段封存、逐段评分、应期事件或缺席状态的裁决协议。当前后端问事轮仍复用既有 chat 并按 `chat-followup-v1` 校验/保存（`backend/app.py:1538–1597`），未引用该候选。若直接复用既有 judge/chat，三段协议会被丢失或按错误 schema 解释，故不能接线。

## 需要 Change Eval 前补齐的最小证据

1. 独立三调用编排图及每调用的输入白名单、输出 schema、manifest/hash 绑定和 fail-closed 状态机。
2. 公开的封存词表/规范化规则/字段检查器，以及缺席、输入损坏、方法不匹配的合成 smoke fixtures。
3. 八字、卦象、综合各自的事件与 abstain 契约，含窗口、指标、阈值、评分和时区规则；评分器与候选提示词分离修改。
4. 新 judge/adapter 与既有 chat/judge 的路由证明；确认不会改变既有协议或把三术结果折叠为单一准确率。
5. 按 INV-10 完成 Change Eval；在候选、评测器/指标代码不混改的前提下，由本人最终批准后才可接线。不得以本审计替代 Change Eval 或人工签署。
