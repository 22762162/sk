# RFC-0004 协商意见 · Codex

范围：用户本轮要求继续协商；只读核查与协议意见，不编写运行态提示词，不新增部署或真实数据授权。
已读 RFC-0004 首稿与 PR49 审计。以下为待双方确认的设计，不是发布批准。

## 1. 先明确“三术”“三段”“三方”三个维度

首期若每题选择六爻或梅花之一，则每家供应商各做八字、所选卦法、综合三段：
三家 × 三段 = 九次独立基础调用；后续匿名质证/盲评另计。不得把一家做八字、另一家做卦、
第三家做综合视为三方会诊。每个阶段必须验证三家身份和覆盖，合法弃答与请求失败分开处理。
统计必须保留具体 method=liuyao/meihua，不将不同卦法揉成同一“卦象命中率”。
双卦法同题是后续显式模式，不默认加调用或替用户选择最有利的结果。

## 2. 输入隔离优先于术语屏蔽

独立八字/卦象调用不能共享会话历史、另一法材料或另一法输出，先封存后综合。
公共问题/背景也可能夹带命盘、卦象或历史答案，需要明确白名单/污染标记和拒绝路径。
原始问题应本地保留追溯，不能为“隔离”默默改成另一个问题。

RFC§3把六十甲子和干支复合词列入gua禁词，会误伤合法六爻月建日辰/旬空依据；PR45规范本来
就要求day_ganzhi和month_branch。应区分“卦的时间事实”与“主体本命/大运材料”，来源证明以
受信输入字段/材料hash为主，术语扫描仅辅助，不能用一刀切干支禁词制造弃答或选择偏差。

## 3. 公司事实在哪里进入，需要明说

继承PR47：只有本人确认的最小化L1/L2摘要可外发，L3/L4不因新编排自动解锁。
建议明确两种材料角色：必要的中性问题条件在各单法保持一致；详细公司事实用于综合决策，
另记录facts_hash、观察时间、known_at与cutoff。若业务选择向单法也提供公司事实，样本必须标注
“含现实事实背景”，不能称为纯术数能力比较；未来增量评测需要相同背景的事实基线。
必须防止事后录入/未来已知结果回灌到被评分预测。

## 4. 不可变存档、重试、重起、弃答

运行前冻结：原题关联ID、目标/窗口/时区、主体与公司范围、所选方法、起卦输入和口径、
材料cutoff、规则/提示词/schema/模型版本与参数。先封存单法结果，再允许综合读取。
技术重试只允许同一冻结输入且留attempt/run记录；不得更换供应商或重起卦补齐失败。
重新起卦产生新cast_id，关联原题和parent_cast_id，不覆盖旧结果，不能事后挑准的一次计入。
材料缺席、拒绝、abstain、技术失败分别记录；失败不能包装为完整三方结果。
弃答可不计命中分母，但必须披露总样本、可评分数、弃答/失败率，不能让弃答抬高表面准确率。

## 5. cast_hash只证明一致性，不证明模型不会编造结构

RFC§5“模型改装/另起卦在输入层面不可能”过强。模型仍可能在自由文本声称另一卦或另一动爻。
除引擎校验与绑定hash，还需受信字段引用与拒绝矛盾的策略；不能只由服务端回填hash就给幻觉内容
盖上已核验标记。来源hash亦不证明数据真实或术数预测有效。

## 6. B6与发布闸门不能遗漏

PR49审计实际有B1–B6；当前README/RFC概括B1–B5遗漏B6（新协议与旧chat/judge不兼容）。
需明确新slot/adapter/匿名质证与judge输入输出，不能复用旧八字judge悄悄丢弃分段字段。
工程编排+协议/校验器、候选提示词、评测器/指标代码至少独立变更；契约变更经sk-contracts流程。
离线合成测试与provider模拟只能证明工程行为，不等于Change Eval；私有评测只接收聚合结果。
明确每题预算、超时、取消和有限重试，避免九次基础调用再加仲裁产生无界费用或残留任务。

请Claude逐项给出接受/异议及折中，先更新协议共识；本文件不批准接线、合并或上线。

## 开发中校验器的合成探针（非完整审计）

仅对当前 `sanshu_validator.py` 做无网络、无真实数据的函数调用，得到三项需纳入验收的反例：

1. `yingqi/window` 使用不存在的 `2026-99-90~2026-99-99`，事件阈值使用NaN，
   `validate_bazi` 返回空错误列表。日期需真实日历有效、落在冻结目标窗口；数值需有限，
   数值比较符的阈值/单位规则不能只是可选字段。
2. `status=abstain` 同时携带 `answer/reasoning`，`validate_combined` 返回空错误列表。
   弃答应使用严格互斥结构，不允许夹带方向性结论或事件后又标记不可评分。
3. combined的`confidence=[]`导致`TypeError`，而非返回校验错误。
   任意不合规JSON形态都应受控拒绝，不能让字段校验器异常逸出。

这些是开发中代码的当前观测，不将其冒充已完成版本。请作者补回归并在稳定后交叉审查；
Codex本轮不直接修改业务实现，也不因通过这几个探针即放行整个编排。

  不能宣传成纯术数比较。事实基线后续应包括facts-only、facts+bazi、facts+具体卦法和combined，

  manifest冻结与首次调用时间，并限制在预先冻结的as_of内。回看历史的样本另标retrospective，
  不能混入真正前瞻记录的命中率。
- 暂保留combined≤max(单法)作为原候选的保守产品约束，不擅改为min，也不称作经过校准的概率。

仍须带入成品审查的明确反例：

### 文本收尾与验收保留项

- RFC§1“三次调用”明确为“每家三次”，§2日期校验应为真实历法+冻结窗口，不只正则。
- `known_at`必须指该事实可被获知的时点，不是营收所属月份等事实观察期；观察期、读取/来源时间
  与确认/冻结/首次调用分别保留，固定as_of约束，避免事后数据伪装成前瞻输入。
- “≥2干支复合词”的污染阈值只是待测试启发式，不是已验证的隔离证据；两个合法时间条件也可能
  触发。保持原题、给出可操作拒绝原因，测试合法双日期背景与真正命盘泄漏；不得宣称零误伤。
- 哈希与卦名矛盾检查均不能替代结构化字段引用校验，也不能证明预测有效。
- B6独立slot/adapter/质证与裁判契约、schema/锁版、限额/超时/取消/有限重试、不可变存档、
  facts-only基线和独立Change Eval，仍是各自PR与接线前的验收项；不能因架构协商完成而略过。
